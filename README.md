TRACK_ID=PS06


A fraud-desk investigation assistant for a bank. It takes a single customer's transaction history, runs it against a small set of deterministic risk rules, and produces an investigation report that either says plainly **"nothing here needs attention"** or lays out exactly which transactions triggered which rule, how they connect, and what to look at first.

The system provides investigation signals and evidence, not a verdict on whether fraud occurred.

---

## How to Run

```bash
pip install -r requirements.txt
python app.py
```

Then open:

```text
http://localhost:8000
```

Set `GEMINI_API_KEY` in the environment before starting the application to enable the LLM narrative layer.

Without an API key, the application still runs fully. The API and UI work end to end, and reports are generated using a deterministic template instead of an LLM narrative.

Each finding contains a `narrative_source` field indicating whether the narrative was generated by Gemini or the deterministic fallback.

The investigation decision never depends on the LLM being available.

## What the System Does

### 1. Deterministic Rule Engine

The deterministic rule engine is implemented in:

```text
src/rules_engine.py
```

This is the only component responsible for deciding whether a transaction pattern should be flagged.

Four rules are evaluated purely in Python against the customer's transaction history:

| Rule | Description                              |
| ---- | ---------------------------------------- |
| R1   | Unusually Large Transfer                 |
| R2   | Burst of Payments to a Newly Added Payee |
| R3   | Odd-Hours Activity                       |
| R4   | Break From Established Pattern           |

### R1 — Unusually Large Transfer

Identifies transactions where the amount is significantly above the customer's own historical median rather than relying on a fixed population threshold.

### R2 — Burst of Payments to a Newly Added Payee

Identifies a payee with no history before the customer's established 30-day baseline that subsequently receives a cluster of payments.

### R3 — Odd-Hours Activity

Identifies transactions occurring between `00:00` and `05:00`.

The rule is gated using the customer's own historical activity during this period so that customers who regularly transact during the night are not incorrectly flagged.

### R4 — Break From Established Pattern

Identifies spending categories that were never present in the customer's baseline history when combined with an above-median transaction amount.

R2 and R4 explicitly avoid treating transactions inside the customer's baseline period as "new."

This prevents cold-start behavior from incorrectly flagging normal activity.

## Payee Normalization

Implemented in:

```text
src/payee_normalizer.py
```

Real transaction descriptions for the same payee may not always be identical.

The system uses Gemini embeddings with:

```text
gemini-embedding-001
```

Unique transaction descriptions are embedded and greedily clustered using cosine similarity.

This allows the system to determine whether descriptions likely represent the same payee rather than relying only on exact string matching.

If the embedding request fails or `GEMINI_API_KEY` is unavailable, the system automatically falls back to exact-string matching.

The fallback is transparent and does not prevent the investigation pipeline from running.

## LLM Narrative Layer

Implemented in:

```text
src/report_builder.py
```

Gemini receives only the already-computed finding from the deterministic rule engine.

The input includes:

* Rule ID
* Rule description
* Exact transaction IDs
* Evidence values
* Relevant transaction information

Gemini is instructed to produce a concise investigator-facing explanation.

The prompt explicitly prevents the model from:

* Claiming that fraud occurred
* Introducing transactions that were not part of the finding
* Creating unsupported evidence
* Making an automated fraud/no-fraud decision

If the Gemini request fails, the system automatically generates a deterministic narrative using the same evidence.

Every finding contains:

```text
narrative_source
```

This indicates whether the narrative originated from Gemini or the deterministic fallback.

## Local Integrity Ledger

Implemented in:

```text
src/ledger.py
```

Every completed investigation report is stored in an append-only, hash-chained ledger.

Each entry contains the hash of the previous entry.

This makes modification of historical reports detectable.

Available endpoints:

```text
GET /api/ledger
```

Displays the ledger chain.

```text
GET /api/ledger/verify
```

Recomputes the hashes from genesis and reports whether the ledger remains intact.

This is a local integrity mechanism and not a distributed blockchain.

There is:

* No external blockchain
* No consensus mechanism
* No mining
* No distributed network

The implementation uses the core concept of hash-linked, tamper-evident history.

## Data

Risk rules are defined in:

```text
data/risk_rules.json
```

The file contains the four rules, threshold parameters, and the rule text cited by investigation reports.

Customer transaction histories are stored in:

```text
data/customers/
```

The dataset contains five deterministic synthetic customers:

| Customer                   | Scenario                                          |
| -------------------------- | ------------------------------------------------- |
| `cust_101_clean`           | Routine history with no findings                  |
| `cust_102_large_transfer`  | Out-of-pattern large transfer                     |
| `cust_103_new_payee_burst` | Burst of payments to a new payee                  |
| `cust_104_odd_hours`       | Large ATM withdrawals during odd hours            |
| `cust_105_pattern_break`   | Large transaction in a previously unused category |

The synthetic dataset is generated using:

```text
scripts/generate_data.py
```

The data generation process is seeded and deterministic.

Each customer history contains a warm-up period that establishes normal payees and categories before the baseline cutoff.

This gives the rule engine a meaningful historical baseline instead of producing false positives caused by cold-start conditions.

### Customer 103 — New Payee Burst

### Customer 104 — Odd-Hours Activity


## Investigation Principles

The system follows several deliberate design principles.

### No Automated Fraud Verdict

The system never states or implies that fraud occurred.

Every report contains a disclaimer explaining that the findings are investigation signals rather than a fraud determination.

### Evidence-Based Findings

Every referenced transaction can be directly checked against the input CSV.

The report does not allow the LLM to introduce new transaction IDs or unsupported evidence.

### Explicit Clean Results

A clean customer history produces an explicit no-findings report instead of silently returning nothing.

### Human Decision Required

The following decisions remain intentionally outside the system:

* Fraud or no-fraud determination
* Account freezing
* Account blocking
* Customer contact
* Other account actions
* Cross-customer pattern detection

The system focuses on investigating one customer's transaction history at a time.
